Post-Quantum TLS Switchover on AWS with Owner-Gated KMS

A security startup wanted proof, on real cloud infrastructure, that a gateway can move from classical to post-quantum hybrid key exchange under live traffic without dropping a request, and that privileged key changes only go through while the enrolled owner is holding their phone. I built the test, ran it on AWS and handed over the raw evidence.

post-quantum tlsaws kmscloudtrailgosecurity engineering

The Brief

The client had already built continuous authentication: a phone keeps checking that the person holding it is the enrolled owner (see the earlier case study). Buyers kept asking two questions. Can your gateway move to post-quantum key exchange without an outage? And does your owner check actually stop a privileged change in a real cloud account, even for an administrator?

The ask was one live run on AWS that answers both, with evidence a third party can check without trusting me: a traffic counter with zero failed, a packet capture showing the key exchange change, a key policy before and after, CloudTrail events for an approved change and for a refused admin call, a screen recording, and every instance shut down afterwards.

What I Built

  • A traffic probe in Go that keeps fresh and persistent TLS connections running, logs every request into a hash-chained file and never retries, so a single dropped request shows up as a failure instead of being hidden.
  • A TLS 1.3 gateway on EC2 whose key exchange curves move from X25519 to X25519MLKEM768 through a hot config reload, without a restart.
  • A governed switch: the reload and the KMS key policy update go through one gateway that accepts the request only with a valid credential and only while the live behavioural scorer reports the owner as present.
  • A KMS key policy with an explicit deny on policy changes for every principal except the governed gateway role and a recovery role. A role with AdministratorAccess cannot change it directly.
  • Evidence tooling: a PCAP reader that pulls the selected group out of every ServerHello, CloudTrail collection, a verifier for the hash chain, and a report generator that refuses to build if any check fails.

The Detail That Needed Care

A TLS connection keeps the key exchange it started with. So "connections stayed open through the switch" would have been the wrong claim. What actually happens is that the reload closes idle keep-alive connections and the client reopens them on the hybrid group. The honest claim, and the one the evidence supports, is zero failed requests, with the capture showing every handshake after the switch on the hybrid group.

I also caught the gateway writing the authentication header into its own access log during rehearsal. The log filter now drops it, the old logs were redacted and the credential was rotated before the final run. Small, but exactly what a reviewer of the evidence would have found.

What This Does Not Claim

This shows a live switchover to a standardised hybrid post-quantum key exchange and an owner-gated control path on a real cloud account. It is not a test against a quantum computer, and the owner check is a behavioural signal, not production biometric certification. The report says both.

Stack

Go (traffic probe, verifier), Caddy for TLS 1.3 with X25519MLKEM768, Python / FastAPI governance gateway, AWS EC2, KMS, IAM and CloudTrail, tshark for the packet capture, a live behavioural scoring service for owner presence, shell tooling for start, stop and teardown.
