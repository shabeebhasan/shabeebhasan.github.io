Dovia: healthcare, closer to people.

Modernizing a doctor-on-demand product means more than replacing its screens. The patient, the professional and the backend all need to agree on what happens next.

Laravel 13React 19React NativePassport authenticationMySQLAPI security

The starting point

An existing 2018–2020 healthcare codebase connected two mobile applications to a Laravel API. It needed a modern web experience, an updated mobile foundation and a coherent identity without breaking the contract its clients already depended on.

My work focused on that modernization: the Dovia patient and web identity, Dovia Pro for professionals, a React frontend integrated into Laravel, mobile compatibility work, and regression coverage around sensitive flows. This case study builds on an existing product; it is not a claim that the original application was authored from scratch.

One backend, three clients

Laravel serves the React web application and the API used by both React Native clients. The web frontend can run on the same origin as the API, while patient and doctor roles get different navigation and workflows. Existing endpoint names and response envelopes are preserved across clients.

A consultation journey people can follow

Patients sign in, confirm their location, search nearby professionals and submit an immediate or scheduled consultation request. Doctors have their own workspace for requests and consultation status. History separates pending, active, completed and cancelled appointments. Profiles, care preferences and medication-request screens share the same identity.

The location should be true, not convenient

A default map centre is useful for display. It is not evidence of where a patient is. The web flow now keeps location empty until GPS succeeds or the user explicitly confirms a point. A late GPS error cannot erase a manually confirmed selection. Doctors can also recover from denied GPS on their pending-request list. Regression tests cover these states, plus local-to-UTC scheduling and daylight-saving gaps.

Security work behind the interface

Profile and location updates cannot promote an account into a doctor or change protected identity fields. Generic patient appointment updates cannot rewrite charges or collected money. Payment methods are owner-scoped, and consultation transitions validate the actor and current state.

Billing work includes linking Stripe checkout sessions to the correct subscription, mapping PayPal renewal events through their agreement identifier, and reserving a durable card-charge attempt before contacting the provider. If the outcome is uncertain, the application blocks another capture instead of blindly retrying. Provider reconciliation remains a release gate.

What is demonstrated, and what remains

The screenshots come from the running Laravel/React application using an isolated database with synthetic accounts. Browser checks exercised patient login, location confirmation, nearby search, consultation creation and history, plus doctor acceptance and completion. Automated checks also cover real mobile booking and polling methods in isolation; both Android and iOS JavaScript bundles build.

Development-stage case study. Live payments, email and professional-verification providers still need environment-specific validation. Native-device lifecycle testing, eight propagated image-size dependency warnings per mobile app, push delivery and ambiguous daylight-saving hours remain tracked. Video, chat, pharmacy fulfilment and family accounts are not presented as delivered. No real patient usage or clinical/compliance certification is claimed.
